## Verdict

The architecture still holds, and so does the tenancy: every new action I read — the
pantry's, action mode's, the AI spend views, the language switch — goes through
`homeDb` or checks the home it was given, and `AiUsage` was scoped automatically,
by the schema-reading rule, the moment it had a `homeId`. That rule has now paid for
itself twice.

What has changed is **where the risk lives**. Three days ago the worst thing a member
could do was fill a list with junk. Now a Save button reaches a paid model, rewrites
the text the member typed, and does it in the same request that saves it. The findings
that matter most in this audit are about that seam:

- **T1** — a long recipe loses the end of its instructions on save. Silently, with no
  error, and nothing in the tests exercises the length where it happens.
- **S1** — the monthly AI limit is a number on a page. Only the importer is rate
  limited; every recipe save and every "prepare" press calls the model unthrottled.
- **M2** — the language work stopped a few files short of done, and nothing would
  notice the next file left in English.

Nothing here is on fire. **T1** is the one I would fix this week: it destroys a
household's own writing, and it does it quietly.

## Security

### S1 — The AI spending limit is a display, and most model calls are unthrottled (Medium, new)

There are now **three** ways into a paid model call, and only one is bounded:

| entry point | calls | rate limited? |
| --- | --- | --- |
| `importRecipeFromUrl`, `importRecipeFromCaption` | `normalizeRecipe` | yes, 8 per 15 min per (IP, user) |
| `createRecipe`, `updateRecipe` | `prepareCookSteps` | **no** |
| `prepareRecipeSteps` (action mode's "prepare" button) | `prepareCookSteps` | **no** |

And `MONTHLY_LIMIT_USD` says in its own comment: *"nothing here stops a call past this,
it only says so."* So the limit a household sees on Settings is advisory, and a member —
or a borrowed session, which is the case the importer's limiter was written for — can
press "prepare" in a loop, or resubmit the edit form with one character changed, and
each press is a billed Sonnet call with up to 12,000 characters of input.

The cost per call is small (cents), which is why this is Medium and not High. But the
reason the importer was rate-limited — *"it is the spending being bounded, not the
mistakes"* — applies to these word for word, and the save path is the one a script
would pick because it is not guarded.

**Fix**, smallest first:

1. The same `checkRateLimit("ai", user.id)` in front of `withCookSteps` and
   `prepareRecipeSteps`. A save that is over the limit still saves — it just clears
   `cookSteps` the way a reader that is down already does, so the existing degradation
   path is the whole of the UX.
2. Make the limit a limit: `getHomeAiSpend` before each call, and treat a home over
   `MONTHLY_LIMIT_USD` exactly like a missing API key — an honest refusal on import,
   plain steps on save. Both paths already exist and are tested.

### S2 — The rate limiter's key can still be varied by the client (Low → Medium, carried S6)

Unchanged in code: `attemptKey` uses the **first** `X-Forwarded-For` entry. On Vercel
the edge overwrites the header, which is why it was Low. It is raised a notch here only
because the key now guards spending as well as logins: if anything in front of the app
ever appends instead of overwriting, the import limit becomes per-request rather than
per-person. `x-vercel-forwarded-for` is the honest header on this platform. The login
timing difference (no bcrypt for an unknown email) is also unchanged.

### S3 — The import guard is a name check (Medium, carried S2, unchanged)

`isBlockedHost` still passes `http://[::ffff:127.0.0.1]/` and any DNS name that resolves
to a private address. **Two more places now call it** — `readCaptionSource` for every
reel source and `importRecipeImage` for poster frames — so the surface is wider, though
the fix is still one function.

Worth adding to what the last audit said: the post-redirect re-check
(`isBlockedHost(new URL(response.url).hostname)`) runs **after** `fetch` has followed
the redirect. It stops the app *reading* an internal response; it does not stop the
request being *sent*. A public page that 302s to an internal address still gets a GET
delivered there. `redirect: "manual"` with the check applied at each hop is the version
that means what the comment says.

### S4 — The model's output is trusted to rewrite the household's text (Low, new, a design note)

`prepareCookSteps` is told the recipe is *"data, not instructions"* and the ingredient
lines are never rewritten — both good. But its answer **replaces
`Recipe.instructions`**, the household's own text, on every save that touches it. A
prompt injection sitting in an imported recipe (the importer's own prompt refuses those,
so it would have to get past that first) gets a second chance on every edit, and what it
can do is limited to rewriting steps — which is the one thing this reader is allowed to
do anyway. I am recording this as a boundary to keep in mind rather than a defect: the
blast radius is one recipe's steps in the home that imported it.

### What is right

- **`AiUsage` was scoped by the rule, not by hand.** It carries a `homeId`, so `homeDb`
  scoped it the moment it existed; `getHomeAiSpend` goes through `homeDb` and the
  installation view says in a comment why it does not. This is the design working.
- **The reel importer runs every source through `safeImportUrl`**, and logs shapes rather
  than bodies — *"a stranger's recipe is not ours to keep."*
- **Action mode's page reads through `homeDb`**, and `prepareRecipeSteps` through
  `recipeInScope`, so another home's recipe id finds nothing on either path (read, not
  driven — the tenancy specs cover the helpers themselves).
- **The service worker's new language cache holds one word**, and switching language
  drops the kept pages rather than serving them in the old one.
- **The importer and the cook-steps reader both carry the "describe before nullish" and
  "nothing narrows" rules**, and both have a unit test that runs the schema through the
  SDK's converter. That is a production failure turned into a guard in two places.

## Stability

### T1 — A long recipe loses the end of its instructions on save (High, new)

This is the finding I would act on first.

- `recipeSchema` accepts `instructions` up to `MAX_BODY` = **20,000** characters
  (`src/lib/form.ts`).
- `userMessage` in `src/lib/cook-steps.ts` sends the model
  `recipe.instructions.slice(0, MAX_INPUT_CHARS)`, with `MAX_INPUT_CHARS` = **12,000**.
- The model is told *"Do not add steps the recipe does not have"*, so it returns steps
  for the 12,000 characters it saw.
- `withCookSteps` writes `read.instructions` — the model's steps, joined — **into
  `Recipe.instructions`**, replacing what was saved.

So any recipe whose instructions run past 12,000 characters has everything after that
point deleted on its next save, with a success message. `lib/cook.ts`'s length guard
does not catch it, because the instructions and the breakdown were rewritten together
and agree with each other perfectly; they just no longer agree with what the cook typed.

It is also not only the first save: `updateRecipe` re-prepares whenever the instructions
change, so an edit to step 2 of a long recipe cuts it again.

12,000 characters is long for one recipe, but not absurd for a pasted blog post or a
bread recipe with a method written out in full, and the importer allows 24,000 on its
side. **Nothing in the tests exercises that range**: no test under `tests/` hands
`prepareCookSteps` or `userMessage` an input longer than `MAX_INPUT_CHARS`.

A related edge I did not measure: `MAX_TOKENS` is 4,000 for the answer. A long recipe
restated as JSON steps could approach that; if it truncates, the parse fails and the
reader reports `unavailable`, which is the safe way to fail. Only the input truncation
fails unsafely.

**Fix**: when `instructions.length > MAX_INPUT_CHARS`, do not send it — return
`unavailable` (plain steps, column cleared) — or raise `MAX_INPUT_CHARS` to `MAX_BODY`
so the two ceilings are one number. The first is one line. A unit test on
`prepareCookSteps` with a long input (no network needed: it returns before the client
is built) holds it.

### T2 — The import's worst case outruns its function (Medium, new)

The recipe routes set `maxDuration = 60`. What an import can spend in sequence:

| step | ceiling |
| --- | --- |
| page fetch, or reel sources one after another (Instagram: 3) | 8 s each → **8–24 s** |
| `normalizeRecipe`, `timeout: 25_000`, `maxRetries: 1` | **up to 50 s** — the SDK timeout is per attempt |
| poster/picture fetch | 8 s |
| `sharp` downscale, `storePhoto` | small |

That is **66 s for a web page and 82 s for a reel** in the worst case, against 60. Past
that the platform kills the function, the cook sees a generic failure, and — if the kill
lands after the model answered — the call was billed and not recorded.

The save path is inside the budget (20 s × 2 = 40 s for `prepareCookSteps`), but only
just, and it is the same shape. **Fix**: an overall deadline carried through the import
(`AbortSignal.timeout` at the top, handed down), or `maxRetries: 0` on the import, where
the paste box already is the retry.

### T3 — A billed call that fails validation is not recorded (Low, new)

In both readers, `recordAiUsage` runs after `client.messages.parse` returns. When the
SDK rejects the answer against the zod schema it **throws**, so the `catch` runs and
the usage row is never written — although Anthropic billed the call. That is exactly
the failure that happened in production with `totalTimeMinutes: 0` (#87): every one of
those imports was paid for and none of them was counted. `APIError.headers` does not
carry usage, but the parse can be split — `messages.create`, record, then validate — so
the row is written whenever there was a response.

### T4 — The reminder job re-sends on a timeout (Medium, carried T3, half fixed)

Members and languages are now fetched once for all homes, which was half the
suggestion. Still open: `sendPushToUsers` runs its own `pushSubscription.findMany` for
each task, serially, and `lastNotifiedAt` is written in one `updateMany` at the end, so
a run that times out partway has sent notifications and recorded none of them.

### T5 — A save racing a "prepare" loses the edit (Low, new)

`prepareRecipeSteps` reads the recipe, waits on the model (seconds), then writes
`instructions` and `cookSteps` unconditionally. If somebody saves an edit in between,
the prepare lands afterwards and writes steps derived from the **old** text over the
new — and if the ingredients changed, indices that point at the old lines. `updateRecipe`
has the same read-model-write shape. Two people editing one recipe inside ten seconds is
rare in a household. The cheap guard is an `updatedAt` (or the old `instructions`) in
the `where` of the write, so a stale answer finds no row.

### What is right

- **A reader that is down never fails a save.** `withCookSteps` clears the column and
  the recipe stores. That is the right call and it is tested.
- **The count guard in `lib/cook.ts`** refuses a breakdown that no longer lines up
  rather than guessing, and an index past the end is dropped on its own.
- **The pantry's combined-line decision** (#84) returns *before* anything is read or
  written beyond the pantry, so asking the question costs no transaction.
- **Setting an item done resets its amount inside the same transaction** as the tick,
  so the offline queue's replay semantics are unchanged.

## Scalability

### C1 — One timezone, one column away (High, carried C1)

Unchanged in code. Worth noting because the argument got easier: #104 added
`Home.language` with a default and threaded it through every page, which is the exact
shape a `Home.timeZone` would take — one column, `sayIn(language)` beside
`homeDb(homeId)`, and a reminder job that reads it per home. The language PR is a
template for this one. **It is also the moment to do it**, before `MealPlan.date`,
`ClearedWeek.week` and `AiUsage`'s month boundary accumulate more rows written under
the assumption.

### C2 — Photos: no quota, no upload rate limit (High, carried C2)

Unchanged. `POST /api/photos` is still the one write in the app that takes a megabyte
per call with no limit of any kind. The importer's limiter is the template.

### C3 — A Save now holds a function for a model's latency (Low, new)

Every create, and every edit that touches the text, waits for `prepareCookSteps` inside
the request — typically several seconds, up to 40. For one household that is a spinner
(which #101 drew well). It is worth knowing as a cost: function-seconds now scale with
recipe saves, and the reading could happen after the save (`after()` from
`next/server`) since the save does not depend on it. Not worth changing now.

### C4 — Carried, unchanged

**C3** (whole recipe corpus on `/recipes` and `/meals`) and **C5** (cross-home reads
without a bound) stand as written in the last audit.

### What is right

- **`AiUsage` is one row per call with `@@index([homeId, createdAt])`**, which is exactly
  the one question asked of it, and cost is stored as integer micro-dollars so sums do
  not drift.
- **The model price is keyed by the model named on the row**, so an old row keeps its
  old price when the table changes.

## Things I decided rather than knew

- **T1 is read off the code, not run against the model.** The three facts — 20,000
  accepted, 12,000 sent, the answer written over the field — are each one line and not in
  doubt. That the model then returns steps only for what it saw follows from being shown
  a truncated text and told not to add steps; I did not spend a billed call proving it,
