## Verdict

The codebase is in good shape and its conventions are mostly holding. Every identifier and
path `CLAUDE.md` names still exists, every "still to do" query uses `UNFINISHED`, no page
reads a picture's bytes, no form action bails out with a bare `return`, and no screen
does date arithmetic on the server's clock. The four AI readers are each bounded by
a per-person limit and the monthly allowance, and every model they send is priced.

What this audit found is mostly at the **edges of the app, where it meets something
else**: Supabase's Data API, ESLint's flat config, the open internet, a push service, a
shared phone. Those are the places a convention cannot reach, because no test in the
suite talks to them. That is how the most serious finding — **S1** — stayed invisible.

## Security

### S1 — Every table was readable and writable through Supabase's Data API (Critical, likely — fixed here)

Production's Postgres is a Supabase project (README, "Deploying to Vercel with
Supabase"). Supabase serves every table in `public` over HTTPS through PostgREST to the
`anon` and `authenticated` roles, and the only thing guarding a table is row-level
security. **No migration ever enabled RLS**, and Supabase's default privileges grant both
roles everything on tables the `postgres` role creates — which is every table Prisma
migrates.

The publishable (anon) key is designed to be public, and this app hands it to every
signed-in phone in `/api/realtime/token`, together with the project URL and an
`authenticated` JWT. With the Data API in its default state, **any member of any
household could read every table** — every home's lists, recipes and tasks, every
account's email and bcrypt hash — **and write them**: `PATCH /rest/v1/User?id=eq.<mine>`
with `{"role":"SUPER_ADMIN"}` would be enough to take the installation.

**Not confirmed against production**, deliberately — probing it would be the attack.
It is "likely" because it depends on two settings at their defaults: the Data API
enabled, and `public` in its exposed schemas. **Check now**: Supabase dashboard →
Advisors → Security Advisor lists "RLS Disabled in Public" for every exposed table, or
Table Editor marks each one "Unrestricted". If either does, assume the data has been
readable since the Realtime key shipped (#157, 30 September) — the first time the app put the key in a browser — and rotate what can be
rotated: `AUTH_SECRET` (signs everyone out), and the Supabase JWT secret.

**Fixed here:** `20261004130000_close_supabase_data_api` turns RLS on for every table in
`public` with no policy (so `anon` and `authenticated` see no rows), revokes their grants,
and revokes their default privileges for tables created later. Prisma connects as the
tables' owner, which RLS does not bind, so the app is unaffected; the migration refuses
to run rather than lock the app out if that ever stops being true. Tried locally against
`anon`/`authenticated` roles made to imitate Supabase's: 2 rows readable before,
`permission denied` after, 0 rows with the grant put back (RLS alone holds),
app unaffected. `tests/integration/rls.test.ts` fails if a later migration adds a table
without RLS, and `CLAUDE.md` now says so beside `homeDb`.

### S2 — The import's address guard could be walked round (High, carried S3 — fixed here)

Carried from the last two audits. `isBlockedHost` checked a URL's hostname as written:

- `http://[::ffff:127.0.0.1]/` — an IPv4 address inside IPv6, which a URL writes as
  `[::ffff:7f00:1]` — passed.
- Any name resolving to a private address (`127.0.0.1.nip.io`, or a domain pointed at
  `10.0.0.5`) passed, because nothing resolved it.
- `redirect: "follow"` meant a public page's 302 to `169.254.169.254` was **requested**
  before the final URL was checked.
- 100.64/10, 198.18/15, multicast and the rest were not listed.

**Fixed here:** `src/lib/safe-fetch.ts` — `safeFetch` follows redirects itself, checks
every hop, resolves every name and refuses it if *any* address is private, and judges an
embedded IPv4 as IPv4. All three import fetches go through it.
`tests/unit/safe-fetch.test.ts` holds each bypass above. **What remains** is DNS
rebinding (a name that resolves publicly when checked and privately a moment later);
closing it needs the connection pinned to the checked address, which on Vercel, with no
private network behind the function, is not worth a custom dispatcher.

### S3 — The tenancy lint rule was switched off on almost every screen (High — fixed here)

`CLAUDE.md` says a lint rule rejects `prisma.list` and friends in pages. It did — until
the untranslated-copy rule was added in a second config block. **ESLint's flat config
does not merge a rule's options across blocks**: the later block's
`no-restricted-syntax` replaced the earlier one for every file both named, and by now that
was nearly every page and component. `eslint --print-config` on the dashboard showed only
the copy selectors. Nothing failed, because a rule that is not running reports nothing.

Separately, the rule's model list was typed by hand and stopped at the seven models that
existed then: `pantryItem`, `mealPlan`, `aisleChoice`, `clearedWeek` and `aiUsage` passed
lint even where the rule did run.

**Fixed here:** the selectors are two named arrays (`TENANCY`, `COPY`), and the copy block
spreads both. The model list is read from `schema.prisma` the way `homeDb` reads it from
Prisma. `tests/unit/lint-rules.test.ts` lints `prisma.pantryItem.findMany()` as a page,
a converted component and an unconverted one, and asks for the error — it fails on the old
config. Turning the rule back on found **no** violations; the guard had lapsed but nobody
had walked through the gap. Also removed the copy list's stale `task-card.tsx`.

### S4 — A push endpoint was any URL at all (Medium — fixed here)

`saveSubscription` stored whatever `endpoint` a signed-in caller sent, and the reminder job
and every cook-mode timer then POST to it from the server — the same reach as S2, with a
daily schedule. Its keys were unchecked strings.

**Fixed here:** the endpoint must be https and pass `assertPublicUrl`; the keys must have
the shape a browser hands out. Held in `tests/integration/push.test.ts`. Sending now has
a 10s timeout per push (`PUSH_TIMEOUT_MS`) — web-push sets none, so one push service that
stopped answering held the whole reminder run.

### S5 — Logging out left the device subscribed to the account (Medium — fixed here)

`CLAUDE.md`: "Logging out takes this browser's copy of the household with it." It took the
pages, the queue and the pictures, but not the push subscription, which lives on the
server against the account. A shared tablet went on hearing the last person's task titles
and timers after they logged out, and `removeSubscription` existed but was never called.

**Fixed here:** `LogoutButton` (`src/components/logout-button.tsx`) removes the
subscription server-side and unsubscribes the browser *before* the session ends — after
it, nothing can say whose the endpoint was — bounded at two seconds so a log-out never
hangs.

### S6 — Smaller hardening (Low — fixed here)

- **Login timing told which emails have accounts** (carried from both earlier audits): an
  unknown email skipped bcrypt. It now compares against a real hash of nothing.
- **A borrowed cookie could guess the current password without limit** on `/profile`. Now
  limited like the login form (`"password"` scope), held in `admin.test.ts`.
- **The rate limiter keyed on the first `X-Forwarded-For`** (carried S2). It now prefers
  `x-vercel-forwarded-for`, which the platform sets and a caller cannot.
- **Photo uploads had no limit of any kind** (carried C2, the rate-limit half). Now 60 per
  quarter-hour per person, answered with a 429 and a sentence; held in `photos.test.ts`.
- **An offline add whose chosen id was taken by a row on another list** was reported as
  applied and added nothing. It now adds under a fresh id; held in `offline-sync.test.ts`.
- **sharp would decode up to 268 MP** from an imported page's picture; now 40 MP.
- **The middleware matcher had drifted again** (carried M2/M4): `/pantry` and `/bars` were
  missing. Pages still check the session themselves, so this was cosmetic; added.

### What is right

- `homeDb`'s design — the scoped set read from the schema, unclassified models an error —
  is the right shape, and S3's fix copies it.
- Every action that takes an id goes through `homeScoped`/`homeDb`; every admin action
  pairs `requireAdmin` with `assertHomeAdmin` on the record's own home; none pairs
  `requireAdmin` with the active home.
- The offline queue rejects per op, and every queued id is checked against the caller's
  homes.
- `readingFor` binds a reading token to the home and to the exact lines, with HMAC
  domain separation from the session JWT.

## Correctness

### K1 — Two model calls could outrun the platform (Medium — fixed here)

`maxDuration = 60` was set on the five recipe routes, and `ai-readers.test.ts` added up
their worst cases. `sortPantry` and `sortListAisles` call the model too (20s, retried
once — 40s) from `/pantry` and `/lists/[id]`, which set nothing, so they ran on whatever
the project default is. **Fixed here:** both set 60, and the budget test now covers them.
The same test also had cold `await import(…)`s of modules reaching Prisma inside test
bodies — the 5s trap `CLAUDE.md` records from 2026-09-25 — now at file level.

## Performance

### P1 — Foreign keys without indexes (Low — fixed here)

Postgres does not index a foreign key's source column. `photoId` on Home, List, Task,
Recipe and PantryItem, `createdById` on Invite, List, Task and Recipe, and `assigneeId`
on Task were unindexed — so every picture deleted or replaced, every account removed,
and every upload's sweep (`photos: { none: {} }` across six tables) was a sequential scan
per table. Small tables today. **Fixed here:** `20261004140000_index_foreign_keys`.

### Open, carried

- **The reminder job** (carried T4) still queries subscriptions once per task and writes
  `lastNotifiedAt` only at the end, so a run that dies partway re-sends tomorrow. The new
  push timeout makes dying partway much less likely; the rest is unchanged.
- **`/recipes` and `/meals` ship the whole recipe corpus** (carried C3) — not re-measured.
- **Two redundant indexes**: `Task(homeId)` is a prefix of `Task(homeId, nextDueAt)` and
  `Photo(homeId)` of `Photo(homeId, createdAt)`. Each costs a write; neither is worth a
  migration on its own.

## Decided rather than known

- **S1's severity** rests on Supabase's defaults, not on production — see S1 for why.
- **The RLS migration refuses to run** if the migrating role neither owns a table nor
  bypasses RLS, rather than risk locking the app out of its own data. Supabase's
  `postgres` role owns everything Prisma created, so it should never trigger.
- **DNS rebinding is left open** (S2): the cost of pinning connections outweighs the risk
  on a host with no private network.
- **Push endpoints are checked for being public, not allowlisted** to known push services:
  an allowlist is stronger but would silently break any browser whose push service is not
  on it.
- **The photo limit is 60 per quarter-hour**, the password limit the login form's 8 — both
  guesses at "only a loop gets here".
- **The logout unsubscribe gives up after 2s** and logs out anyway.
