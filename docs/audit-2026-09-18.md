# Code audit — 18 September 2026

Commit audited: `3e5748a`. Four pillars, as asked: maintainability, stability, security,
scalability.

Everything below was checked against the code as it stands, not inferred from the
documentation. `npm run lint`, `npm run typecheck`, `npm run db:check`, 173 unit tests
and 372 integration tests all pass on this commit. The browser suite was not run (no
Chromium in the audit environment); CI runs it on every push.

## Verdict

| Pillar | Grade | The short version |
| --- | --- | --- |
| Maintainability | **A−** | Genuinely excellent. No TODOs, no `any`, no `@ts-ignore`, one raw query. The main risk is that CLAUDE.md is becoming the bottleneck, not the code. |
| Stability | **B** | One confirmed production-only bug, and two places where a slow day turns into a failed write rather than a slow one. |
| Security | **B−** | The tenancy model is the best part of this codebase. The recipe importer is the weak point and is exploitable today. |
| Scalability | **C+** | Correct and fast for a household. Three specific things stop it at "a few hundred homes", and one of them stops it at the first home outside Denmark. |

The headline: this is a well-built app whose architecture is sound. Nothing here asks for
a rewrite. The findings are a fix list, roughly a week of work, and the top four are worth
doing before the next feature.

## Security

### S1 — The recipe importer's SSRF guard can be walked around (High)

`src/lib/recipe-import.ts:71` — `isBlockedHost` inspects the **hostname as written**, and
the request is made to whatever that hostname *resolves to*. Four concrete bypasses, all
verified against this function:

| Input | Blocked? | Reaches |
| --- | --- | --- |
| `http://2130706433/` | no | 127.0.0.1 (decimal-encoded IPv4) |
| `http://0x7f000001/` | no | 127.0.0.1 (hex-encoded IPv4) |
| `http://attacker.example/` with an A record of `169.254.169.254` | no | instance metadata |
| `http://100.64.1.1/` | no | carrier-grade NAT / container networks |

The first two were demonstrated end to end: Node's `fetch` resolved both and returned the
body of a loopback server. The third needs no trickery at all — the check never sees an IP
address, so it returns `false` and `fetch` does the resolving.

Three smaller gaps in the same function: `100.64.0.0/10`, `192.0.0.0/24` and
`198.18.0.0/15` are absent; there is no port restriction, so an internal service on any
port is reachable once a hostname gets through; and the redirect check at
`recipe-import.ts:354` runs on `response.url` **after** `redirect: "follow"` has already
made the internal request. The body is not returned, but the request happened.

The fix is to stop checking names and start checking addresses: resolve the hostname with
`dns.promises.lookup({ all: true })`, reject if **any** returned address is in a private
range, pin the connection to a vetted address (an undici `Agent` with a custom `connect`,
or `lookup`), and use `redirect: "manual"` so each hop is validated before it is followed.
Restrict to ports 80 and 443 while you are in there. The range test itself should take a
parsed IP, not a string — `net.isIP` plus explicit CIDR checks, including the
IPv4-mapped-IPv6 form (`::ffff:127.0.0.1`).

This is the one finding I would fix this week.

### S2 — Nothing limits how often the importer fetches (High)

`src/app/actions/recipe-import.ts:12` — `importRecipeFromUrl` checks `requireHomeUser()`
and then fetches. There is no rate limit, no per-home budget, no concurrency cap. Each
call costs up to 8 seconds, 3 MB of page, 15 MB of image, and a `sharp` decode of that
image on the server.

Any member of any home can therefore use the deployment as an outbound HTTP client at
whatever rate they like — a port scanner with S1, a bandwidth amplifier without it, and a
denial-of-service against your own function budget either way. `checkRateLimit` already
exists in `src/lib/rate-limit.ts` and takes a scope; `checkRateLimit("import", user.id)`
is a two-line fix.

### S3 — Changing a password needs no current password, and nothing revokes a session (Medium)

`src/app/actions/admin.ts:40` and `:245` — `profileSchema` asks for a name and a new
password. It does not ask for the existing one. Somebody who gets a phone left unlocked,
or a session cookie, can take the account permanently rather than temporarily.

The other half of the same problem: sessions are stateless JWTs (`src/lib/auth.ts:27`)
with a 30-day expiry and no version, no `jti`, no server-side record. So a password change
does not invalidate anything, `logout` only clears the cookie on the device it was pressed
on, and a leaked token is good for a month with no way to cut it off.

Two independent fixes. Require the current password in `updateOwnProfile` (verify with
`verifyPassword` before writing). Then add a `sessionVersion Int @default(0)` to `User`,
put it in the JWT claims, compare it in `getCurrentUser`, and bump it on password change —
which also gives you a working "sign out everywhere" and a way to cut off a stolen token.

### S4 — No text field has a maximum length (Medium)

`src/lib/form.ts:23` — `requiredText` is `.trim().min(1)`. `optionalText` has no bound at
all. Neither has a `.max()`, and no schema in the app adds one. Every title, note,
ingredient block and instruction block accepts as much as the Next server-action body
limit allows (1 MB by default).

It is bounded, so it is not unbounded storage growth — but a 1 MB list title is rendered
on `/lists`, on `/dashboard`, and in the RSC payload of both, on every visit, for
everybody in the home. Add `.max()` to the two helpers (200 for a title, 2000 for notes,
50 000 for ingredients and instructions) and every schema inherits it at once. This is the
cheapest fix on the list and the most broadly applicable.

### S5 — The rate limiter is keyed on the client's IP (Low)

`src/lib/rate-limit.ts:13` — the key is `sha256(scope:ip:identifier)`. An attacker
rotating source addresses gets a fresh 8-attempt budget per address, per email. bcrypt at
cost 10 is then the only brake on password guessing, at roughly 100 ms and one function
invocation per try.

Keeping the IP in the key is right — it is what stops one attacker locking a real person
out. Add a second, IP-independent counter on the identifier alone, with a higher ceiling
(say 50 failures in 15 minutes per email, whoever is asking), so a distributed attempt hits
a wall that changing address does not move.

### What is right, and worth saying plainly

- **`homeDb` is the best thing in this repo.** Reading the scoped-model set from
  `Prisma.dmmf` rather than a hand-kept list, refusing unclassified models outright, and
  pinning the whole arrangement with a schema-walking unit test — that is separation that
  holds by construction rather than by memory. The `NO_HOME_ID` `refuse: true` distinction
  is subtle and correctly reasoned.
- Permission checks are consistently the right shape. `requireAdmin` is never paired with
  the active home; `assertHomeAdmin` always takes the id the action was given;
  `canAdministerCurrentHome` is used exactly where the home comes from the session.
- Invite codes are hashed, compared in constant time, and expire. `presentsCronSecret`
  treats a missing secret as "no admittance" rather than "no password required", which is
  the failure mode that usually gets this wrong.
- `/api/photos/[id]` answers 404 rather than 403 for another home's picture, and the
  housemate-avatar exception is asked only after the cheap check fails.
- Security headers in `next.config.ts` are the right set, and the note explaining why
  there is no full CSP is honest rather than a shrug. Worth revisiting once you want one:
  Next 15 supports nonce threading through middleware, so it is a day's work rather than
  an architectural change.
- `npm audit` reports 5 advisories (4 high). All are build-time only — `deepmerge-ts` via
  the Prisma CLI, `postcss` via Next — and `audit fix --force` downgrades Prisma and breaks
  the build, exactly as CLAUDE.md says. Leaving them is correct. Re-check on each Next and
  Prisma release rather than treating the decision as permanent.

## Stability

### T1 — The "Not your home" screen never appears in production (High, confirmed)

`src/app/(app)/error.tsx:22`:

```ts
const denied = error.message === "Not allowed";
```

In a production build, Next.js replaces server-thrown error messages with a generic string
and a digest before they reach the client — the redaction is in
`next/dist/server/app-render/create-error-handler.js`, and the message it substitutes is
*"The specific message is omitted in production builds to avoid leaking sensitive
details."* So `denied` is always `false` in production.

What a user actually sees on a cross-home URL is "Something went wrong", with a **Try
again** button that re-runs the same denied render and fails identically, forever. The
friendly, correct, well-written "Not your home" copy below it is dead code in the only
environment that matters.

No test catches this: the integration tests call the actions directly (where the message
survives), and `e2e/tenancy.spec.ts` only asserts 404s on pages, never the error screen.

The fix is to stop matching on the message. Either throw a typed error and set its
`digest` to a stable sentinel you can compare (`error.digest?.startsWith("NOT_ALLOWED")`),
or — better, and simpler — have `assertHomeAccess` call `notFound()` instead of throwing,
which is already the behaviour on page reads and needs no error boundary at all. Then add
an e2e case that drives a denied *action* and asserts what the user sees.

### T2 — The reminder job is one unbounded invocation, and a timeout re-sends everything (Medium)

`src/app/api/cron/reminders/route.ts:44` fetches every due task across every home with no
`take`. Line 80 then calls `sendPushToUsers` **once per task** inside a sequential loop —
and `sendPushToUsers` (`src/lib/push.ts:23`) issues its own `pushSubscription.findMany` on
every call, so the query count is linear in tasks, not in homes.

Only after that loop finishes does line 88 write `lastNotifiedAt` for the whole batch, in
one `updateMany`.

Three things follow. The function's wall time grows with installation size and will
eventually exceed Vercel's limit. When it does, **nothing** is marked as notified, so the
next run re-sends every notification that did go out. And `finishCronRun` never runs
either, so the run row stays open and `getHealth` reports a stale, degraded schedule that
is actually working.

Fix in three steps, smallest first: hoist the subscription lookup out of the loop (one
`findMany` for all recipients, grouped by user — removes the N+1 outright); mark each task
notified as it is sent, or in batches, rather than all at the end; then page the task query
and either self-invoke for the next page or move to a queue once one run stops fitting.

### T3 — A long recipe can time out its own transaction (Medium)

`src/app/actions/lists.ts:340` — `addRecipeIngredients` opens an interactive transaction
and then, per ingredient, awaits a `listItem` write and a `listItemSource.upsert` in
sequence. That is two sequential round trips per line, all inside one transaction.

Prisma's default interactive-transaction timeout is 5 seconds. A 30-ingredient recipe is 60
sequential queries; at 40 ms of pooled round trip each — plausible on a serverless
connection to a remote Postgres — that is 2.4 seconds, and the margin is not large. A
timeout rolls back the whole add, which is the right behaviour but a bad experience.

Restructure to two set operations instead of a loop: a `createMany` for the lines that are
new, a `updateMany`/`$executeRaw` bump for the ones already there, and one `createMany`
with `skipDuplicates` for the source rows. That is three queries regardless of recipe
length. If the loop is worth keeping for clarity, at minimum raise the timeout explicitly
(`{ timeout: 20_000 }`) so the limit is a decision rather than a default.

### T4 — A thrown action replaces the page instead of filling in the footer (Low)

`src/components/use-form-action.ts:28` awaits the action with no `try`/`catch`. A rejected
promise propagates out of the transition and up to the route error boundary, so a dialog
that could have shown "That belongs to a different home" in the footer it already renders
instead takes the whole page down to the error screen — which, per T1, is the wrong error
screen.

Wrap the await, and on a throw set `{ ok: false, error: "Something went wrong — try
again." }`. Real crashes still reach the boundary through `onRequestError`; the person
filling in the form keeps what they typed.

### T5 — Two migrations share a timestamp (Low)

`prisma/migrations/20260916140000_add_user_photo` and
`prisma/migrations/20260916140000_home_theme` have identical prefixes. Prisma orders
lexicographically, so `add_user_photo` runs first — correct today, by alphabetical luck
rather than intent. Harmless now; worth knowing about before someone adds a third.

### What is right

- `startCronRun` before any work, so a job that dies still leaves evidence it started, is
  exactly the right shape for the failure mode where "no reminders" and "no schedule" look
  identical.
- The optimistic-update handling in `src/components/list-items.tsx` mirrors the server's
  behaviour precisely, including dropping `sources` on tick — the kind of detail that
  usually drifts.
- Both error boundaries exist and `global-error.tsx` correctly assumes nothing about
  styling having loaded.
- The test suite is strong: 545 unit and integration tests, 22 browser specs, and the two
  documented races (optimistic tick, `/recipes/new` matching the saved-recipe pattern) are
  the two that actually bite.

## Scalability

### C1 — One timezone, hardcoded, for the whole installation (High)

`src/lib/time.ts:11`:

```ts
export const TIME_ZONE = "Europe/Copenhagen";
```

`Home` has no timezone column. Every due date, every "today", every reminder hour, for
every household, is Copenhagen.

For the second home this is invisible. For the first home in another timezone it is wrong
in a way nobody reports as a bug — tasks come due at odd hours, the dinner suggestion turns
over at the wrong moment, and the daily reminder arrives whenever 06:00 UTC happens to be
locally. Of everything in this audit, this is the single clearest blocker to the specific
goal of "more homes".

The work is mechanical because `lib/time.ts` is already the only place that knows: add
`timeZone String @default("Europe/Copenhagen")` to `Home`, thread it through the six
exported functions as a parameter, and let the call sites pass the home's value. Both test
suites already run at `TZ=UTC`, so the change is verifiable where it was written.

### C2 — Photo bytes in Postgres, with no quota and no CDN (High)

Each `Photo` row carries up to 1.2 MB plus a 200 KB thumbnail
(`src/lib/photo-file.ts:28`). Nothing anywhere limits how many a home may have: not
`/api/photos`, not `storePhoto`, not the sweep. Every uncached read pulls the full blob
out of Postgres, through a serverless function, to the browser
(`src/app/api/photos/[id]/route.ts:58`).

CLAUDE.md justifies this well for a household — no second service, nothing to keep in
step — and for a household it is the right call. At 1 000 homes averaging 50 pictures it is
roughly 70 GB of database that has to be backed up, restored and paged through for every
thumbnail on every cold browser cache.

You do not need to move to object storage today. You do need a per-home cap now, before
the data exists: a `photo.count` check in `storePhoto` against a constant, refused with a
message. That buys the time to decide, and it is ten lines. The `immutable` cache header
already does the right thing for repeat views; what is missing is a shared cache, and the
`private` directive correctly forbids one as long as the bytes are behind a session.

### C3 — Several reads have no upper bound (Medium)

- `src/app/(app)/lists/[id]/page.tsx:23` loads **every** item on a list, ticked ones
  included. CLAUDE.md states plainly that a shopping list keeps everything ticked off as
  next week's vocabulary — so this collection only grows, and a two-year-old weekly
  shopping list is a page that gets slower every week and never gets faster.
- `src/app/actions/lists.ts:322` loads all of them again on every "add to list".
- `src/app/(app)/admin/homes/page.tsx:11` loads every home on the installation with four
  relation counts each, with no pagination — the page most directly in the path of "more
  homes".

For the list page, the fix is to page the ticked section (it is already behind a
`Collapsible`, so it is the natural place to load on demand). For the admin page, take a
page at a time.

### C4 — Counting open items by fetching their ids (Medium)

`src/app/(app)/lists/page.tsx:17` and `src/app/(app)/dashboard/page.tsx:25` both do:

```ts
items: { where: { done: false }, select: { id: true } },
```

and then read `.length`. That transfers one row per open item, per list, per page load,
purely to produce a number.

Prisma supports filtered relation counts, and I verified it works against this exact
schema and client version:

```ts
_count: { select: { items: true, /* and */ items: { where: { done: false } } } }
```

(as two aliased entries, or a single filtered count plus the existing total). One integer
instead of N rows, on the two most-visited pages in the app.

### C5 — The recipes page ships the whole corpus to the browser (Low)

`src/app/(app)/recipes/page.tsx:17` selects every recipe with full `ingredients` and
`instructions` and hands them to a client component for filtering. The reasoning in
`recipe-directory.tsx` is sound and explicitly scoped — "dozens rather than thousands" —
and I would not change the approach. Two notes: `instructions` is in the payload but is
never searched (only title, description and ingredients are), so it is pure weight on every
page load; and it is worth writing down the number at which this flips to server-side
filtering, so the decision gets revisited on purpose rather than when someone complains.

### C6 — Two smaller ones (Low)

`revalidatePath("/", "layout")` fires on every home edit, profile edit and home switch
(`src/app/actions/admin.ts`), invalidating the entire app's cache for a change that affects
one header. And `sweepUnclaimedPhotos` only runs after a successful upload
(`src/lib/photos.ts:113`), so a home that uploads once and abandons the form keeps that
stray forever — the reminder job is already a daily pass over everything and is the natural
place to sweep across homes.

### What is right

- Index coverage is genuinely good. `@@index([homeId, nextDueAt])` on `Task`,
  `@@index([key, createdAt])` on `LoginAttempt`, `@@index([homeId, createdAt])` on `Photo`
  for the sweep — each one matches a query that actually exists.
- The dashboard's four queries run in one `Promise.all`, and the mine/theirs split is done
  in memory off a single result rather than as a second round trip. Correct call.
- `RecipeSuggestion` caching the day's pick, keyed `@id` on `homeId` so the shape cannot
  drift, is a small feature done exactly right.
- The cascade and `SetNull` choices on the schema are deliberate throughout, and the
  `NoAction`-vs-`Restrict` note on `RecipeCategoryLink` is a real Postgres subtlety caught
  before it bit.

## Maintainability

This pillar needs the fewest words, because the code is in good shape. Some numbers:

- 111 source files, ~10 700 lines. Largest file is 503 lines. No god objects.
- **Zero** TODO/FIXME/HACK comments. Zero `any`. Zero `@ts-ignore`. Zero
  `dangerouslySetInnerHTML`. One raw query, and it is `SELECT 1` in a health check.
- Three `eslint-disable` lines, each with a reason attached.
- Lint and typecheck clean. 545 unit and integration tests pass.
- The custom `no-restricted-syntax` rules in `eslint.config.mjs` encode the tenancy
  invariants as lint errors with explanatory messages. This is the right way to make a
  convention survive the person who wrote it.

Four things worth acting on.

### M1 — CLAUDE.md is becoming the bottleneck (Medium)

638 lines, 40 KB, and edited in **22 of the last 40 commits** — the most-changed file in
the repository by a wide margin. It is doing three jobs at once: a map of the codebase, a
decision log explaining why each alternative was rejected, and a style guide.

The prose is excellent and the reasoning is worth keeping. But every change now carries a
documentation edit to a file that a newcomer has to read in full before touching anything,
and the "why we tried the other thing first" narratives — which are most of the bulk — are
exactly the part that does not need re-reading on every visit.

Split it: keep CLAUDE.md as the map and the non-negotiable rules (perhaps 200 lines), and
move the decision narratives to `docs/decisions/`, one file per decision, linked from the
rule they justify. Nothing is lost, the rules stay findable, and a change touches one small
file instead of one large one.

### M2 — The middleware matcher is a hand-kept route list, and it has already drifted (Medium)

`src/middleware.ts:24` enumerates eight route prefixes. `/bars` is not among them. It is
not a security hole — `(app)/layout.tsx` calls `requireUser()`, which is the real gate —
but it is the pattern working exactly as it will keep working: silently, every time
somebody adds a page and does not remember this file.

Invert it. Match everything except `_next/static`, `_next/image`, `favicon.ico`, the public
API routes and `PUBLIC_PATHS`, so a new page is protected by default and an exception is
something you have to write down.

### M3 — Temporary scaffolding shipped (Low)

`src/app/(app)/bars/page.tsx` says so itself: *"A temporary page... Delete this once the
question is answered. It is a measuring stick, not a feature."* It is in production. Either
the question is answered and it goes, or it is not and the page should say what is still
outstanding.

### M4 — The photo choreography is repeated five times (Low)

`createList`/`updateList`, `createTask`/`updateTask`, `updateRecipe`, `updateHome` and
`updateOwnProfile` each perform the same five steps: `readPhotoChoice`, bail on failure,
read the previous `photoId`, write, then `discardReplaced`. The comment explaining *why*
`discardReplaced` comes last is copy-pasted four times, which is a fair signal.

One helper — `withPhoto(homeId, formData, previousPhotoId, write)` — removes around 40
lines and, more usefully, removes the chance of a sixth photo-carrying model being added
with the discard step forgotten.

## Suggested order

Roughly a week, and the first four are worth doing before the next feature.

1. **S1** — fix the SSRF guard properly (resolve-then-check, pin the address, manual
   redirects, port allowlist).
2. **S2** — rate-limit the importer. Two lines; `checkRateLimit` already exists.
3. **T1** — stop matching on `error.message`; add an e2e case for the denied-action path.
4. **S4** — add `.max()` to `requiredText` and `optionalText`.
5. **C1** — move `TIME_ZONE` onto `Home`, before there is data to migrate.
6. **C2** — a per-home photo cap. Ten lines, and it has to land before the data exists.
7. **T2** — hoist the subscription lookup out of the reminder loop; mark tasks notified
   as they are sent.
8. **S3** — require the current password; add a session version.
9. **C4** — filtered relation counts on the lists page and the dashboard.
10. **M2** — invert the middleware matcher.

**T3**, **C3**, **M1**, **M3**, **M4** and the remaining low findings are worth doing but
are not urgent.

## Things I decided rather than knew

- **T1** is reasoned from Next.js's documented production redaction and the presence of the
  redaction string in the installed `next` runtime, not from a production build served and
  clicked through. I am confident, but it is worth a five-minute confirmation against a
  `next build && next start` before the fix is designed around it.
- **T3**'s 40 ms-per-round-trip figure is an estimate for a pooled serverless connection to
  a remote Postgres. The structural point — 2N sequential queries inside one transaction,
  against a 5-second default — holds regardless of the number, but whether it is currently
  *failing* depends on your actual latency and recipe lengths.
- **C2**'s 70 GB figure assumes 1 000 homes × 50 photos × 1.4 MB. The shape of the problem
  is what matters, not the arithmetic.
- I did not run the browser suite (no Chromium available here), so the e2e specs are
  assessed by reading rather than by running. CI runs them on every push.
