# Code audit — 20 September 2026

A read-only review at `bf18c00` ("Give the meal-plan swipe a visible slide…"), covering
security, stability, scalability and maintainability, plus the housekeeping question:
what can be deleted.

It is the second of these. The first is `docs/audit-2026-09-18.md`, which lives on
`claude/code-audit-four-pillars-4xschg` and **was never merged** — so its findings were
never tracked anywhere the repository can see them. Every one of them has been re-checked
against this commit rather than assumed, and one of them turns out to have been wrong.
Where a finding is carried over it keeps a pointer to its old number.

## Verified on this commit

Everything was actually run, against a real Postgres, rather than assessed by reading:

| | result |

The test suite is in genuinely good health, and it was worth the cost: the tenancy,
theme, offline and validation specs are all doing real work, and the parallel-database
machinery from #60 held up on a machine it had never run on.

**The browser suite needs its own note, because my first reading of it was wrong.** It
appeared to pass at this commit and had not run at all: the container ships Chromium
build 1194 while this Playwright wants 1243, every test errored on the missing binary,
and the exit code was lost to a `| tail` in the command that invoked it — a shell
pipeline reports the status of its *last* stage, so `tail`'s success was read as
Playwright's. Pointing Playwright at `/opt/pw-browsers/chromium` fixes it, and the suite
does pass — but by the time that was working the fixes at the end of this document were
already applied, so **the figure I have (250 passing, 3.8 min) is for the fixed tree,
not for `bf18c00`**. Subtracting the one spec added below, `bf18c00` would be 249, which
is arithmetic rather than a measurement and is written here as such.

This is recorded rather than tidied away because "the suite passed" is the claim a
reader is least likely to check, and it is exactly the kind of thing the correction
further down takes the previous audit to task for.

## Verdict

The architecture is still the strongest thing here, and nothing in this audit disturbs
it. `homeDb` reading its scoped-model set from `Prisma.dmmf` and refusing what nobody
classified is the single best decision in the repository, and the multi-tenancy it
guards holds everywhere I pushed on it.

What has changed since 18 September is that **the codebase grew faster than its
invariants were re-checked**. Three of this audit's findings are things that were fine
two days ago and are not now, because a feature landed on top of them:

- `addMealPlanIngredients` (#74) multiplied a single-recipe write into a whole week's,
  inside a transaction that already had no timeout set (**T1** — the headline).
- `/meals` (#63, #66) joined `/recipes` in shipping the home's entire recipe corpus,
  ingredients included, to the browser on every page load (**C3**).
- `CLAUDE.md` went from 26 KB to 79 KB in three days (**M1**).

Nothing here is on fire. **T1** is the one I would fix this week; it is a real failure a
household can hit today, on a button the app invites them to press.

### The correction

The last audit's headline security finding was that `isBlockedHost` could be walked past
with `http://2130706433/` and `http://0x7f000001/`, "demonstrated against a local
server". **That is not true of this commit, and I do not believe it was true of the
previous one either.** `safeImportUrl` reads `url.hostname` *after* `new URL()` has
parsed it, and the WHATWG URL parser normalises every one of those encodings to a dotted
quad before the guard ever sees it. Run against the guard exactly as written:

```
BLOCKED http://127.0.0.1/          (hostname: 127.0.0.1)
BLOCKED http://2130706433/         (hostname: 127.0.0.1)   <- decimal
BLOCKED http://0x7f000001/         (hostname: 127.0.0.1)   <- hex
BLOCKED http://017700000001/       (hostname: 127.0.0.1)   <- octal
BLOCKED http://127.1/              (hostname: 127.0.0.1)   <- short form
BLOCKED http://2852039166/         (hostname: 169.254.169.254)
BLOCKED http://0/                  (hostname: 0.0.0.0)
ALLOWED http://[::ffff:127.0.0.1]/ (hostname: [::ffff:7f00:1])   <- this one is real
```

The last line is the finding that survives, and it is a different shape — see **S2**.
Worth saying plainly: an audit that claims a demonstrated exploit and is wrong is worse
than one that says nothing, because it spends the reader's trust on the findings that
*are* right. I have tried to mark below exactly which claims I ran and which I reasoned.

## Security

### S1 — Logging out does not take the household's photographs with it (Medium, confirmed)

`public/sw.js` keeps two caches. `homehub-pages-v1` holds rendered pages, and
`homehub-assets-v1` holds `/_next/static/`, the icon, the manifest — **and
`/api/photos/*`**, which is the actual image bytes of a household's home, lists, tasks,
recipes and members' faces.

`ForgetOfflineData` on the login page clears the queue and posts `homehub:forget`. The
worker's handler is:

```js
if (event.data && event.data.type === "homehub:forget") {
  event.waitUntil(caches.delete(PAGES));
}
```

`PAGES` only. The photographs stay, indefinitely — nothing expires them, `VERSION` has
never been bumped past `v1`, and they are served **cache-first**, so the server's
session check never runs for them again.

This defeats the stated guarantee, which CLAUDE.md puts in so many words: *"Logging out
takes this browser's copy of the household with it."* It does not. Two consequences:

- On a shared family tablet, person B's session leaves person A's photographs sitting in
  Cache Storage on disk, readable by anything with origin access.
- Somebody removed from a home keeps a working copy of that home's pictures in their
  browser. `/api/photos/<id>` would now 404 them; cache-first means it is never asked.

**Fix**, and it is genuinely one line — drop the pictures, keep the hashed chunks so the
app does not re-download itself:

```js
if (event.data && event.data.type === "homehub:forget") {
  event.waitUntil((async () => {
    await caches.delete(PAGES);
    const assets = await caches.open(ASSETS);
    for (const request of await assets.keys()) {
      if (new URL(request.url).pathname.startsWith("/api/photos/")) {
        await assets.delete(request);
      }
    }
  })());
}
```

`e2e/offline-lists.spec.ts` already drives a genuinely offline browser, so this is
testable the same way: log in, view a photo, log out, assert the cache entry is gone.

### S2 — The import guard is a name check, not an address check (Medium)

`isBlockedHost` refuses literal private addresses and `localhost`. It cannot refuse:

1. **An IPv4-mapped IPv6 literal.** `http://[::ffff:127.0.0.1]/` parses to hostname
   `[::ffff:7f00:1]`, which is not `::1`, does not start with `fe80:`, `fc` or `fd`, and
   is allowed. *Run and confirmed against the guard.* Whether the fetch then reaches
   loopback depends on the runtime having IPv6 — **I could not confirm that half**: this
   sandbox has no IPv6 at all (`listen ::` returns `EAFNOSUPPORT`), so the connection
   failed for the wrong reason. On a dual-stack Linux host, which Vercel's runtime is,
   `::ffff:127.0.0.1` routes to loopback.
2. **Any DNS name that resolves to a private address.** `internal.example.com` with an
   `A` record of `10.0.0.5` passes the guard untouched, as does a rebinding name that
   answers publicly once and privately on the second lookup. This one needs no IPv6 and
   no cleverness about encodings — it is structural. A hostname allowlist cannot express
   "what does this resolve to".

The redirect re-check (`new URL(response.url).hostname`) has the same blind spot, since
it is the same function.

**What this is worth.** On Vercel the blast radius is small: there is no internal network
to speak of, and `169.254.169.254` is blocked by literal. It is not nothing — it is a
signed-in member turning the app into a fetch proxy that speaks from the app's IP — but
it is a hardening job, not an emergency. The proper fix is to resolve the host first
(`dns.promises.lookup`, `all: true`), refuse if any answer is private, and pin the
connection to the address that was checked. That is a real piece of work; adding
`::ffff:` to the IPv6 branch is ten minutes and closes the half I could demonstrate.

### S3 — The importer has no rate limit of any kind (Medium, carried S2)

`importRecipeFromUrl` calls `requireHomeUser()` and then fetches. Nothing else. Each call
is up to two outbound requests (page, then image), 3 MB and 15 MB bounded, 8 s timeout
each, plus a `sharp` downscale. A signed-in member can drive that in a loop.

`checkRateLimit` already exists and already works across serverless instances. It is
scoped by string, so this is `checkRateLimit("import", user.id)` and a branch. The same
argument applies to `POST /api/photos` — see **C2**.

### S4 — A password changes without the old one, and nothing revokes a session (Medium, carried S3)

`updateOwnProfile` writes a new `passwordHash` on the strength of the session cookie
alone. And the session is a bare JWT with `sub` and a 30-day expiry: there is no version,
no `iat` floor, no store to check against. So:

- Somebody with a borrowed session takes the account outright, and
- changing the password does **not** end the sessions that were already open — including
  the attacker's, which is the one moment the owner thinks they have just fixed it.

Two separate fixes, and the second is the one that matters. A `tokenVersion` column on
`User`, bumped on password change and carried in the JWT, is a small migration and a
comparison in `getCurrentUser`, and it turns "change your password" into something that
actually does what everybody assumes it does.

### S5 — No text field has a maximum length (Medium, carried S4)

`requiredText` is `.trim().min(1, message)` and `optionalText` is `.trim().optional()`.
Neither has a `.max()`, and nor does anything built on them. Nor do a recipe's
`ingredients` and `instructions`, which are `z.string().trim().optional()`. The only
bounded fields in the app are a task's interval and a list item's amount.

So a member can store a megabyte as a list's title, and every page that draws that list —
the dashboard included — carries it. The database will take it: Postgres `text` is
1 GB. Nothing here is an escape; it is a household member being able to make the app
unusable for their household, and a row that cannot be got rid of through the UI once it
is too big to render.

A `.max()` on `requiredText`/`optionalText` and on the two recipe bodies is a handful of
lines and one `readForm` test.

### S6 — The rate limiter trusts a client-supplied header (Low, carried S5)

```ts
const forwarded = headerList.get("x-forwarded-for") ?? "";
const ip = forwarded.split(",")[0]?.trim() || headerList.get("x-real-ip") || "unknown";
```

The **first** entry of `X-Forwarded-For` is the least trustworthy one: it is whatever the
client sent, unless the edge overwrote the header rather than appending to it. Vercel does
overwrite, which is why this is Low rather than High — but the code does not know that,
and the key is `scope:ip:email`, so anything that does vary the perceived IP gives
unlimited attempts per email. On Vercel the honest reading is `x-vercel-forwarded-for`,
or the last entry rather than the first.

Worth pairing with the observation that **login leaks whether an address has an account**:
`if (!user || !(await verifyPassword(...)))` skips bcrypt entirely for an unknown email,
so the two answers differ by ~100 ms. Comparing against a dummy hash costs one constant
and closes it.

### What is right, and worth saying plainly

- **`homeDb`.** Reading the scoped set from `Prisma.dmmf`, refusing unclassified models
  outright, and pinning the judgement half with `home-scoping.test.ts` is the reason the
  tenancy tests are boring. I went looking for a way past it and did not find one.
- **Every server action is guarded**, and guarded the right way: an action given a home
  id checks *that* id with `assertHomeAdmin`; the ones taking the home from the session
  ask `canAdministerCurrentHome`. The `requireAdmin`-plus-active-home trap CLAUDE.md
  warns about is not present at any call site.
- **`/api/photos/<id>`** answers 404 rather than 403 for anything unreachable, and the
  housemate's-avatar special case is asked only after the ordinary check has failed.
- **`photo-file.ts`** measures the bytes rather than believing `Content-Type`, and reads
  only the header, so it never allocates a picture to reject one.
- **`lib/embed.ts`** is an allowlist that rebuilds every embed URL from parsed parts.
  There is not one `dangerouslySetInnerHTML`, `eval` or `innerHTML` in `src/`.
- **`presentsCronSecret`** is constant-time and treats a missing secret as no admittance.

## Stability

### T1 — "Add this week to a list" can exceed its own transaction timeout (High, carried T3 and now worse)

This is the finding I would act on first, because it is reachable from a button today.

`writeRecipesToList` (`src/app/actions/lists.ts:346`) wraps the whole write in one
interactive transaction and, inside it, runs **two sequential round trips per ingredient
line** — an `update` or `create`, then a `listItemSource.upsert`. No `timeout` option is
passed here or anywhere else in `src/`, so Prisma's default of **5 seconds** applies.

Until #74 the worst case was one recipe. `addMealPlanIngredients` now passes **one entry
per day cooking it** — up to seven recipes, deliberately including repeats:

```
7 recipes × ~12 ingredient lines × 2 round trips = ~168 sequential queries, one transaction
```

At 20–40 ms per round trip on a pooled serverless connection to Postgres — *an estimate,
not a measurement; I had only a local socket here* — that is **3.4 to 6.7 seconds**,
straddling the limit. It fails as `P2028 Transaction already closed`, which is a throw,
which lands on the error boundary as "Something went wrong" (and see **T2** — in
production it cannot even say which). Nothing is written, and the cook has no idea
whether half their shopping arrived.

Three fixes, roughly in order of how much they are worth:

1. **Stop making two round trips per line.** The `listItemSource` rows can be written in
   one `createMany({ skipDuplicates: true })` after the loop instead of an `upsert` each.
   That halves it on its own.
2. **Raise the timeout explicitly.** `{ timeout: 20_000 }` says what the ceiling is
   rather than inheriting a default nobody chose.
3. **Batch the item writes.** The existing rows are already in `byText`, so the
   increments and the creates could largely be two statements rather than 84.

The integration tests cover what this action *means* very well. What they do not cover is
its size: `tests/integration/meal-plan-ingredients.test.ts` should have a case with a
seven-day week of substantial recipes, which is also the test that would have caught this.

### T2 — The "Not your home" screen never appears in production (Medium, carried T1)

`src/app/(app)/error.tsx` decides which of two screens to draw with:

```ts
const denied = error.message === "Not allowed";
```

`assertHomeAccess` throws `new Error("Not allowed")` on the server. Next redacts a server
error's message before it reaches a client error boundary in production, replacing it with
a generic string and a `digest`. So `denied` is always `false` on the deployed app, and
somebody who follows a stale link to another household's list is told "Something went
wrong. Trying again often clears it" — advice to retry something that will never work.

*Reasoned from Next's documented redaction, not observed on the deployment* — the local
dev server does not redact, which is exactly why this survived. The fix is to stop
matching on the message: throw a class with a stable `digest`, or have the scoped
helpers `notFound()` instead of throwing, which is arguably the truer answer anyway.

### T3 — The reminder job is one unbounded invocation (Medium, carried T2)

`sendDueReminders` has three problems that compound:

- `prisma.task.findMany` for every due task **across the whole installation**, with no
  `take`.
- A `for` loop over those tasks, each calling `sendPushToUsers`, each of which runs its
  own `pushSubscription.findMany`. That is one query per due task, serially.
- `task.updateMany({ lastNotifiedAt })` only at the **end**. A run that times out
  partway has sent real notifications and recorded none of them, so tomorrow's run sends
  them all again.

The `CronRun` row is opened before the work, which is good and is why this would at least
be *visible*. Fetching the subscriptions once for all the homes involved — the same move
already made for `homeMember` just above it — removes the per-task query, and moving the
`updateMany` inside the loop in batches makes a timeout cost a few duplicates rather than
a full replay.

### T4 — A slow database makes itself slower (Low, new)

The `slow-query-log` extension in `src/lib/prisma.ts` writes a `SlowQuery` row for every
call over the threshold. Under normal conditions that is a handful a day. Under the
condition it exists to observe — a database that has gone slow — *every* query crosses
the threshold, and each one now triggers an additional insert. The instrumentation adds
load in exact proportion to the trouble it is reporting.

It is `void`-ed and `.catch(() => {})`-ed, so it cannot fail a request, and `record`
skips its own model. What is missing is a ceiling: sampling above some rate, or a cheap
in-process counter that stops writing after N in a minute.

### T5 — Two migrations share a timestamp (Low, carried T5)

```
20260916140000_add_user_photo
20260916140000_home_theme
```

Prisma applies migrations in lexicographic order, so these two are ordered by their
suffix (`add_user_photo` before `home_theme`) rather than by when they were written. They
are independent, so nothing is broken. It is worth knowing about because the failure mode
if a future pair *were* dependent is a migration failing inside the production build,
which is the one failure with no rollback.

### T6 — Adding an item is read-then-write with no constraint behind it (Low, new)

`addItem` looks for a matching row with `findFirst` and then creates one if there is
none. There is no unique index on `(listId, lower(text))`, so two phones adding "Milk"
within the same moment both find nothing and both create a row. `nextPosition` has the
same shape and can hand two items the same position.

For a household this is unlikely and the consequence is cosmetic — a duplicate row, or a
tie in an ordering. Recording it because the offline queue makes concurrent writes more
plausible than they used to be, not because it needs fixing now.

### What is right

- **The offline design is the best-reasoned part of the app.** Every op carrying the
  state it wants rather than a delta, the browser choosing the row id so a replay lands
  on the same row, `setItemDone` counting the week only when the row actually changed,
  and the endpoint being a route rather than an action because the browser may have
  crossed a deploy — that is four separate correct calls in a row.
- **`applyQueuedOps` rejects rather than throws**, so one bad op cannot take nineteen
  good ones with it. The applied/rejected/failed distinction is exactly right.
- **The test database machinery** (#60) does what it says. Keying a worker's database on
  the process id rather than `VITEST_POOL_ID`, refusing any name without the right
  suffix, and holding all of it in `test-db-url.test.ts` without a database — all of it
  held up on a machine it had never run on.
- **`weekWorkload`** and its "being owed wins" rule is the kind of thing that is wrong in
  most codebases, and `tests/integration/week.test.ts` pins it with a real clock.

## Scalability

### C1 — One timezone, hardcoded, for the whole installation (High, carried C1)

`TIME_ZONE` in `src/lib/time.ts` is `Europe/Copenhagen`, for everybody. Every date the
app reasons about goes through it: a task's due date, a meal plan's day, a cleared week's
Monday, the reminder job's end-of-day.

For the household this is built for, it is correct and simpler than the alternative. It
is listed as a scale finding because it is the clearest ceiling on the product: a home in
another country is not a feature away, it is a column on `Home`, a parameter through
every function in `time.ts`, and a re-read of `streak.ts`, `week.ts` and `meals.ts`. The
time to add the column is before there are stored dates that were written under the
assumption.

### C2 — Photo bytes in Postgres, with no quota and no limit on uploads (High, carried C2)

The decision to keep bytes in Postgres is well argued in the schema and I am not
re-litigating it. What is missing is the consequence of it:

- **No quota.** `getHomeStorage` measures beautifully and nothing acts on the number.
  Nothing refuses an upload because a home is already large.
- **No rate limit on `POST /api/photos`.** A signed-in member can post 1.2 MB pictures
  as fast as the connection allows. The sweep only collects uploads nobody attached,
  after an hour.
- **The database is the CDN.** Every thumbnail on a twenty-card directory is a serverless
  invocation and a row read. The year-long `immutable` cache header is the only thing
  standing between the app and doing that on every scroll, and it is a good one — but a
  cold cache on a phone is twenty function calls.

A cap per home, checked in `storePhoto` against `getHomeStorage`, is the smallest useful
version and it reuses code that already exists.

### C3 — Two pages now ship the whole recipe corpus to the browser (Medium, carried C5, wider)

`/recipes` did this already. `/meals` now does it too, and with more per row:

```ts
db.recipe.findMany({
  orderBy: { title: "asc" },
  select: { id, title, description, photoId, ingredients, categories: {...} },
})
```

Every recipe in the home, **`ingredients` included**, on every load of `/meals` — for the
picker's search and for the suggestion ranking. The code comments defend this honestly
("two hundred rows is nothing for the DOM"), and for two hundred rows they are right:
call it 200 KB of RSC payload. At a thousand recipes with real ingredient lists it is
more like a megabyte, on a page a household opens on a phone to answer one question about
one evening.

Not worth changing now. Worth writing down as the trigger: **when a home passes roughly
500 recipes, the picker's search has to move to the server.** The suggestion ranking is
already a pure function over candidates, so it is the search box, not the ranking, that
would have to change.

### C4 — Open items are counted by fetching their ids (Medium, carried C4)

On `/lists` and the dashboard:

```ts
include: {
  _count: { select: { items: true } },
  items: { where: { done: false }, select: { id: true } },
}
```

Every open item row is fetched so that `list.items.length` can be read. A household with
twelve lists averaging fifty open items pulls 600 rows to produce twelve numbers.

Prisma has supported a filtered relation count for several major versions, so this is a
straight substitution:

```ts
_count: { select: { items: true, items: { where: { done: false } } } }
```

Two call sites, no behaviour change, and it is the cheapest genuine win in this document.

### C5 — The cross-home reads have no upper bound (Medium, carried C3)

Most unbounded `findMany` calls in the app are scoped to one home and therefore bounded
by how much one household writes, which is fine. Three are not:

- `cron/reminders/route.ts:44` — every due task on the installation.
- `cron/reminders/route.ts:66` — every member of every home involved.
- `lib/storage.ts` — the union scans every content table; unfiltered for the super
  admin's view, and that page runs it on every load.

The first two are **T3**'s. The third is the super admin's alone and runs rarely, but it
is worth knowing that Admin → System costs a full scan of the installation's content.

### What is right

- **`pg_column_size(p.bytes)` column-by-column on `Photo`, and `t.*` everywhere else.**
  Noticing that the composite form would pull every picture through the connection to
  weigh it is the kind of thing that gets found in production, not in review.
- **`@@id([homeId, week])` and `@@id([homeId, date])`** bound `ClearedWeek` and
  `MealPlan` by construction. Neither table can grow faster than the calendar.
- **`RECENT_LOOKBACK`, `HISTORY_WEEKS`, `SWEEP_LIMIT`, `DASHBOARD_LISTS`, `MAX_OPS`** —
  the bounds that *are* there are all in the right places and all explained.
- **The dashboard taking `DASHBOARD_LISTS + 1`** to know whether to offer "See all",
  rather than counting.

## Maintainability

### M1 — CLAUDE.md has trebled in three days (High, carried M1, much worse)

```
2026-09-17   25,762 bytes
2026-09-18   36,942 bytes
2026-09-20   78,911 bytes   (1,184 lines)
```

That is roughly **20,000 tokens that every session must read before doing anything**, and
it grew by 42 KB in two days. The previous audit called it "becoming the bottleneck"; at
this rate it is the bottleneck.

The prose itself is excellent and I would not want it lost — the explanations of why the
band is opaque, why leftovers point at a day, why `UNFINISHED` is `{ NOT: FINISHED }`,
are the reason a session can be useful here at all. The problem is shape, not quality:
it is one file mixing three different things.

- **Invariants** a change must not break (`homeDb` refuses unclassified models; never
  pair `requireAdmin` with the active home; every "still to do" query uses
  `FINISHED`/`UNFINISHED`). These must stay in front of every session.
- **Rationale** for decisions already made and unlikely to be revisited (five paragraphs
  on the status-bar band, the full history of the theme colour). Valuable, referred to
  rarely.
- **Feature walkthroughs** that duplicate what the code's own comments already say
  better, beside the code.

Splitting the second and third into `docs/` and leaving CLAUDE.md as the invariants plus
links would get it back under 20 KB without deleting a sentence. The band history alone
is about 4 KB of a question that is settled.

### M2 — The middleware matcher is a hand-kept route list, and it has drifted (Medium, carried M2, now confirmed)

`src/middleware.ts` lists nine path prefixes. `/bars` is a page under `(app)` and **is not
one of them**, which is the drift the last audit predicted, now actual.

It is not a hole — `(app)/layout.tsx` calls `requireUser()`, so the page redirects anyway
— and that is precisely the point: the matcher is a performance optimisation whose
correctness nothing checks, and a route added without touching it silently stops being
gated at the edge. An allowlist (`matcher: ["/((?!login|accept-invite|api|_next|.*\\..*).*)"]`)
inverts the default so that forgetting is safe.

## Things I decided rather than knew

- **T1's 20–40 ms per round trip is an estimate**, for a pooled serverless connection to
  a managed Postgres. I measured nothing: this sandbox talks to a local Unix socket,
  where the same transaction completes in well under a second. The *shape* — 168
  sequential round trips inside a transaction with a 5 s default — is read straight off
  the code and is not in doubt. Whether it crosses 5 s in production depends on a number
  I could not take. It is worth taking before deciding how hard to fix it.
- **S2's second half is unconfirmed.** That `[::ffff:127.0.0.1]` passes `isBlockedHost`
  is run and certain. That the fetch then reaches loopback is not: this container has no
  IPv6 stack, so the request failed for an unrelated reason. Do not quote it as a
  demonstrated exploit — which is the mistake the last audit made in the other direction.
- **T2 is reasoned, not observed.** Next's production redaction of server error messages
  is documented, and the code matches on the message, so the conclusion follows. I did
  not stand up a production build to watch it happen. It would take ten minutes and is
  worth doing before the fix.
- **C3's "roughly 500 recipes" is a judgement**, not a measured cliff. The real trigger
  is payload size on a phone, and the number depends entirely on how long a household's
  ingredient lists run.
- **The branch classification is from pull-request state, not from git.** Every PR here
  was squash-merged, so ancestry says "unmerged" for all 46. I cross-referenced PR
  `merged_at` against each branch, and separately checked `git diff main...branch` for the
  six branches with no PR. Four of those six have an empty diff, which is the stronger
  evidence; the other two are the audit and the invite-email work.
- **I did not treat the merged-but-undeleted branches as a risk**, only as noise. Nothing
  reads them and nothing deploys from them — `vercel.json` disables every branch but
  `main`.
- **Nothing in the app was changed by this audit**, deliberately, as with the last one.
  Every finding above names its fix; none of them is applied.

## Acted on in this branch

The audit above is a snapshot of `bf18c00` and its findings are written as they stood
there. Three were fixed on this branch afterwards, at the user's direction; the rest are
untouched.

- **T1** — `writeRecipesToList` now collects the item/recipe pairings as it writes the
  items and saves them in a single `createMany({ skipDuplicates: true })`, which halves
  the round trips inside the transaction, and passes an explicit
  `{ timeout: WRITE_TIMEOUT_MS }` of 20 s in place of Prisma's inherited 5. A new
  integration case plans a genuinely full week — seven recipes, twelve distinct lines
  each — and asserts all 84 items and all 84 pairings land.
- **S1** — `forgetThisHousehold()` in `public/sw.js` now takes the `/api/photos/` entries
  out of the asset cache as well as dropping the page cache, and the login-redirect path
  calls the same function rather than its own `caches.delete(PAGES)`. The hashed chunks
  are left alone. `e2e/logout-forgets.spec.ts` asks the browser what is actually left in
  Cache Storage; **it was confirmed to fail against the unfixed worker** (three photo
  entries surviving logout) before being confirmed to pass against the fixed one.
- **C4** — `openItemCounts` in `src/lib/list-counts.ts` counts the open items for a
  whole home in one aggregate, and `/lists` and the dashboard no longer fetch an item
  row per open item to read `.length` off the array. Worth recording what the probe
  found on the way: `_count.select` cannot carry `items: true` and
  `items: { where: … }` together — the duplicate key silently collapses and the query
  returns the *filtered* number under the total's name, which is a wrong answer rather
  than an error. Hence two aggregates rather than one.

Verified after the changes, with every exit code captured directly rather than through
a pipe: lint clean, typecheck clean, `db:check` clean, **792 tests across 42 files**
(unit and integration together, up one on the 791 at `bf18c00` — the full-week case
above), and **250 browser tests** in 3.8 minutes. All green.

The browser run used a throwaway config pointing at `/opt/pw-browsers/chromium`, for the
version mismatch described at the top. Nothing about that config is committed: the repo's
`playwright.config.ts` is untouched, and CI installs the browser its own lockfile asks
for.
